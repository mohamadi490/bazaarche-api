## ۱. هدف سند و قالب ADR

این سند «چرایی» تصمیمات معماری مهم را ثبت می‌کند — نه فقط «چه چیزی» تصمیم گرفته شده (که در سایر اسناد فنی توضیح داده شده). هدف: وقتی ۶ ماه بعد کسی بپرسد «چرا از فلان روش استفاده نکردیم؟»، پاسخ در این سند موجود باشد، نه فقط در حافظه یک نفر.

هر ADR این قالب ثابت را دارد:

| بخش | محتوا |
|---|---|
| **وضعیت** | Proposed / Accepted / Superseded by ADR-0XX |
| **زمینه (Context)** | چه مسئله‌ای باعث این تصمیم شد؟ |
| **تصمیم (Decision)** | چه چیزی انتخاب شد؟ |
| **جایگزین‌های بررسی‌شده** | چه گزینه‌های دیگری مطرح و رد شدند، و چرا؟ |
| **پیامدها (Consequences)** | چه چیزی به‌دست آمد، چه چیزی از دست رفت/سخت‌تر شد؟ |
| **شرط بازبینی** | (در صورت وجود) تحت چه شرایطی باید این تصمیم دوباره بررسی شود؟ |

## ADR-001: Modular Monolith به‌جای Microservices برای Backend

**وضعیت:** Accepted

**زمینه:** تیم در ابتدای مسیر است و باید یک MVP را سریع عرضه کند. Microservices از روز اول overhead عملیاتی بالایی (چند Deploy مستقل، Service Discovery، Distributed Tracing، پیچیدگی تراکنش‌های بین‌سرویسی) تحمیل می‌کند که با اندازه تیم و مرحله فعلی محصول هم‌خوانی ندارد.

**تصمیم:** یک Backend مونولیتیک با مرزبندی دامنه‌ای دقیق (Domain Modules با ساختار ثابت `router/service/repository/schemas/models`؛ جزئیات در `product-development-document.md` بخش ۴).

**جایگزین‌های بررسی‌شده:**
- **Microservices از ابتدا** — رد شد؛ overhead عملیاتی و پیچیدگی هماهنگی بین‌سرویسی برای تیم کوچک و MVP توجیه ندارد.
- **مونولیت بدون مرزبندی دامنه‌ای (Big Ball of Mud)** — رد شد؛ مرزبندی ضعیف باعث می‌شود استخراج آینده به سرویس مجزا عملاً غیرممکن شود.

**پیامدها:**
- ✅ سرعت توسعه بالا، Deploy واحد و ساده، تراکنش‌های بین‌ماژولی (مثل کسر موجودی هنگام سفارش) در یک تراکنش دیتابیسی ساده قابل‌مدیریت.
- ⚠️ در صورت رشد شدید ترافیک/تیم، نیاز به استخراج ماژول‌های پرترافیک (مثل `catalog`) به سرویس مستقل در آینده وجود دارد — به همین دلیل مرزبندی دامنه‌ای از ابتدا رعایت شده.

**شرط بازبینی:** رشد قابل‌توجه ترافیک یا تیم (چند تیم مستقل که روی ماژول‌های متفاوت کار می‌کنند) — طبق رودمپ Phase 3+.

## ADR-002: PostgreSQL + Redis به‌عنوان دیتابیس/کش اصلی

**وضعیت:** Accepted

**زمینه:** نیاز به یک RDBMS پایدار با پشتیبانی قوی از تراکنش (برای صحت مالی سفارش/پرداخت) و یک لایه Cache/Queue سبک.

**تصمیم:** PostgreSQL 16+ به‌عنوان دیتابیس اصلی، Redis برای Cache، Session Rate-limiting، و Broker صف پس‌زمینه.

**جایگزین‌های بررسی‌شده:**
- **MongoDB/NoSQL** — رد شد؛ داده فروشگاهی (سفارش، موجودی، پرداخت) رابطه‌ای و نیازمند تراکنش ACID قوی است.
- **MySQL** — بررسی و رد شد به نفع PostgreSQL به‌دلیل پشتیبانی بهتر از `JSONB`، `Full-Text Search` بومی، و تطابق بهتر با اکوسیستم Async پایتون (`asyncpg`).

**پیامدها:**
- ✅ تراکنش قوی، ابزار بالغ، پشتیبانی خوب از نوع داده‌های موردنیاز (`jsonb`, `tsvector`).
- ⚠️ نیازمند دانش عملیاتی DBA برای مقیاس‌دهی (Backup، Replica) که در سند شماره ۲ پوشش داده شده.

## ADR-003: UUID به‌عنوان کلید اصلی تمام جداول

**وضعیت:** Accepted

**زمینه:** شناسه ترتیبی (`bigserial`) در URLهای عمومی (`/orders/{id}`) قابل‌حدس‌زدن است و اطلاعات کسب‌وکاری (مثل تعداد کل سفارش‌ها) را افشا می‌کند.

**تصمیم:** استفاده از `UUID` (نسخه ۴، از طریق `gen_random_uuid()`) به‌عنوان کلید اصلی همه جداول کسب‌وکاری.

**جایگزین‌های بررسی‌شده:**
- **`bigserial` + شناسه نمایشی جدا** — رد شد؛ پیچیدگی نگه‌داری دو شناسه موازی برای هر منبع.
- **ULID** — بررسی شد (مزیت: قابل مرتب‌سازی زمانی، ایندکس بهتر)؛ برای MVP به نفع سادگی و پشتیبانی بومی‌تر `UUID` در PostgreSQL/SQLAlchemy کنار گذاشته شد؛ قابل بازبینی در آینده اگر کارایی ایندکس UUID تصادفی مشکل‌ساز شود.

**پیامدها:**
- ✅ امنیت بهتر (عدم افشای شمارش داخلی)، آمادگی برای معماری توزیع‌شده احتمالی آینده.
- ⚠️ حجم ایندکس بزرگ‌تر و Locality پایین‌تر نسبت به کلید ترتیبی — قابل قبول در مقیاس فعلی.

## ADR-004: `VARCHAR + CHECK` به‌جای PostgreSQL native `ENUM`

**وضعیت:** Accepted

**زمینه:** فیلدهای وضعیت (`orders.status`, `payments.status`) به‌احتمال زیاد در فازهای بعد مقادیر جدید می‌گیرند (مثلاً وضعیت جدید سفارش).

**تصمیم:** استفاده از `VARCHAR` + `CHECK constraint` به‌جای Type `ENUM` بومی PostgreSQL.

**جایگزین‌های بررسی‌شده:**
- **PostgreSQL native ENUM** — رد شد؛ افزودن مقدار جدید به Enum بومی (`ALTER TYPE ... ADD VALUE`) محدودیت تراکنشی دارد و در برخی نسخه‌ها/ابزار Migration دردسرساز است.

**پیامدها:**
- ✅ انعطاف بالا برای افزودن وضعیت جدید فقط با یک Migration ساده تغییر `CHECK`.
- ⚠️ اعتبارسنجی مقدار کمی ضعیف‌تر از Type بومی (اما در سطح Pydantic هم دوباره اعتبارسنجی می‌شود، پس ریسک عملی پایین است).

## ADR-005: لایه Payment Gateway انتزاعی (Abstract)

**وضعیت:** Accepted

**زمینه:** درگاه پرداخت نهایی هنوز قطعی نیست (طبق موارد `[TBD]` سند شماره ۱) و احتمال افزودن چند درگاه در Phase 2 وجود دارد.

**تصمیم:** طراحی یک Interface مشترک برای درگاه پرداخت (جدول `payment_gateways` + کد قابل‌افزودن پشت یک Abstraction در Service Layer) به‌جای Hardcode یک درگاه خاص در منطق سفارش.

**جایگزین‌های بررسی‌شده:**
- **پیاده‌سازی مستقیم و اختصاصی یک درگاه در منطق سفارش** — رد شد؛ افزودن درگاه دوم در آینده نیازمند بازنویسی منطق `orders`/`checkout` می‌شد.

**پیامدها:**
- ✅ افزودن درگاه جدید بدون تغییر منطق سفارش، فقط با افزودن یک Implementation جدید.
- ⚠️ کمی انتزاع اضافه در MVP که فقط یک درگاه فعال دارد — پذیرفته‌شده چون هزینه آن پایین و بازگشت آن (جلوگیری از بازنویسی) بالاست.

## ADR-006: JWT (Access + Refresh Token) برای احراز هویت

**وضعیت:** Accepted

**زمینه:** API باید Stateless بماند (NFR-007) تا امکان افزایش افقی Replica بدون نیاز به Session مشترک وجود داشته باشد.

**تصمیم:** JWT با Access Token کوتاه‌مدت + Refresh Token برای تمدید نشست.

**جایگزین‌های بررسی‌شده:**
- **Session-based Auth (ذخیره سرور)** — رد شد؛ نیازمند Sticky Session یا Session Store مشترک (Redis) که پیچیدگی اضافه به همراه دارد و با اصل Stateless بودن API در تضاد جزئی است.

**پیامدها:**
- ✅ Stateless، مقیاس‌پذیر، مناسب برای دو Frontend مستقل.
- ⚠️ نیاز به مدیریت دقیق Revocation (جدول `refresh_tokens` طبق سند شماره ۲) چون JWT به‌خودی‌خود قابل ابطال فوری نیست.

## ADR-007: camelCase در API JSON، snake_case داخلی Python/DB

**وضعیت:** Accepted

**زمینه:** Backend پایتون از قرارداد `snake_case` پیروی می‌کند؛ اکوسیستم TypeScript/Angular از `camelCase`. یکی از این دو باید در مرز API تطبیق داده شود.

**تصمیم:** خروجی/ورودی JSON در سطح API همیشه `camelCase` (با `alias_generator` در Pydantic)؛ کد داخلی Python همچنان `snake_case`.

**جایگزین‌های بررسی‌شده:**
- **snake_case در همه‌جا (از جمله JSON)** — رد شد؛ باعث می‌شد کد Angular/TypeScript از قرارداد استاندارد خودش خارج شود یا نیاز به تبدیل دستی مکرر در Frontend باشد.

**پیامدها:**
- ✅ هر دو سمت (Python، TypeScript) با قرارداد طبیعی خودشان کار می‌کنند.
- ⚠️ یک لایه تبدیل (Alias) اضافه در Pydantic — هزینه ناچیز، خودکار.

## ADR-008: PostgreSQL Full-Text Search در MVP به‌جای Elasticsearch/Meilisearch از ابتدا

**وضعیت:** Accepted

**زمینه:** جستجوی محصول در MVP نیاز به قابلیت پیشرفته (Typo-tolerance، Ranking پیچیده) ندارد و حجم داده اولیه پایین است.

**تصمیم:** استفاده از `tsvector`/Full-Text Search بومی PostgreSQL در Phase 1؛ مهاجرت به Meilisearch/Elasticsearch در Phase 2/3.

**جایگزین‌های بررسی‌شده:**
- **راه‌اندازی Elasticsearch از روز اول** — رد شد؛ زیرساخت و پیچیدگی عملیاتی اضافه (یک سرویس جدا برای نگه‌داری) بدون نیاز واقعی در MVP توجیه ندارد (اصل YAGNI).

**پیامدها:**
- ✅ سادگی زیرساخت در MVP، بدون سرویس جانبی اضافه.
- ⚠️ کیفیت جستجو محدودتر از موتور اختصاصی — پذیرفته‌شده تا زمان نیاز واقعی.

**شرط بازبینی:** رشد حجم محصول/ترافیک جستجو در Phase 2/3، طبق رودمپ سند اصلی.

## ADR-009: Trunk-Based Development به‌جای GitFlow کامل

**وضعیت:** Accepted

**زمینه:** محصول با ریتم Deploy مکرر (نه انتشار فصلی) توسعه می‌یابد؛ GitFlow سنتی با شاخه‌های طولانی‌عمر (`develop`, `release/*`) برای این ریتم سربار غیرضروری ایجاد می‌کند.

**تصمیم:** یک شاخه اصلی همیشه Deploy-پذیر (`main`) + شاخه‌های کاری کوتاه‌عمر؛ جزئیات کامل در `git-workflow-branching-guideline.md`.

**جایگزین‌های بررسی‌شده:**
- **GitFlow کامل** — رد شد؛ برای تیم کوچک با Deploy مکرر، هماهنگی چند شاخه بلندمدت هزینه بیشتری نسبت به فایده دارد.

**پیامدها:**
- ✅ سادگی، Merge سریع، تاریخچه خطی و خوانا.
- ⚠️ نیاز به انضباط تیمی بالاتر برای نگه‌داشتن Feature Branchها کوتاه (چند روز، نه چند هفته).

## ADR-010: کنار گذاشتن Nx Monorepo — سه Repository کاملاً مستقل

**وضعیت:** Accepted (به‌روزرسانی معماری — این تصمیم، تصمیم اولیه طراحی Frontend در `product-development-document.md` و `git-workflow-branching-guideline.md` را جایگزین می‌کند؛ هر دو سند بر همین اساس به‌روزرسانی شدند)

**زمینه:** طراحی اولیه (سند معماری اصلی، بخش ۵.۱) یک Nx Monorepo شامل هر دو اپلیکیشن Angular (`storefront`, `admin-panel`) به‌همراه کتابخانه‌های مشترک (`shared/ui`, `shared/data-access`, ...) پیشنهاد داده بود، با هدف جلوگیری از تکرار کد و هماهنگی بهتر Build/Test.

پس از بررسی، تصمیم گرفته شد که **در مرحله فعلی از Nx استفاده نشود**؛ دلیل اصلی: کاهش پیچیدگی و overhead یادگیری/راه‌اندازی ابزار Monorepo (پیکربندی `nx.json`، مفهوم `affected`، مدیریت `libs`) در مرحله شروع پروژه، در حالی‌که تیم هنوز اسکلت پایه Backend/Frontend را راه‌اندازی نکرده است. ساده‌ماندن ابزار در این مرحله بر بهینه‌سازی زودهنگام برای اشتراک کد اولویت داده شد (اصل YAGNI که در سند شماره ۱۲ - Coding Style Guide - نیز تصریح شده).

**تصمیم:** ایجاد **دو پروژه Angular کاملاً مستقل** با ابزار استاندارد Angular CLI (بدون Nx)، هرکدام در **Repository Git جداگانه**:

- `storefront-frontend`
- `admin-panel-frontend`

در کنار `backend-api` (که از ابتدا Repository جدا بود)، مجموعاً **سه Repository مستقل** پروژه را تشکیل می‌دهند.

**جایگزین‌های بررسی‌شده:**
- **حفظ Nx Monorepo (تصمیم اولیه)** — کنار گذاشته شد؛ به‌دلیل هزینه یادگیری/راه‌اندازی بالاتر از فایده آن در مرحله فعلی پروژه.
- **Angular CLI Workspace چندپروژه‌ای بدون Nx (یک Repository، دو پروژه Angular در کنار هم بدون ابزار Nx)** — بررسی و رد شد؛ چون هدف کاهش پیچیدگی *و* استقلال کامل چرخه توسعه/Deploy دو اپ بود، نه فقط حذف ابزار Nx؛ یک Workspace مشترک همچنان یک نقطه تداخل نسخه Angular/Dependency بین دو اپ باقی می‌گذاشت.
- **یک بسته npm خصوصی برای کد مشترک از ابتدا** — رد شد؛ در این مرحله حجم کد واقعاً مشترک (غیر از مدل‌های Generated از OpenAPI) بسیار کم است تا هزینه نگه‌داری یک بسته npm جدا را توجیه کند.

**پیامدها:**

| مثبت | منفی / Trade-off |
|---|---|
| راه‌اندازی سریع‌تر، بدون یادگیری مفاهیم Nx (`affected`, `libs`, `nx.json`) | تکرار جزئی کد بین دو اپ (عمدتاً کلاینت Generated از OpenAPI که در هر Repo جدا تولید می‌شود — ریسک پایین چون Generated است نه دستی) |
| استقلال کامل چرخه Build/Test/Deploy/Versioning هر اپ | نبود بهینه‌سازی خودکار نوع `nx affected` — بدون نیاز واقعی، چون هر Repo از ابتدا فقط شامل یک پروژه است |
| ریسک پایین‌تر تداخل Dependency/نسخه Angular بین دو اپ | عدم امکان یک PR واحد که هم‌زمان هر دو Frontend را تغییر دهد؛ هماهنگی تغییرات مشترک باید دستی (با ارجاع Ticket/PR بین Repoها) مدیریت شود — جزئیات در `git-workflow-branching-guideline.md` بخش ۱۲ |
| Onboarding ساده‌تر برای عضو جدید تیم که فقط روی یکی از دو اپ کار می‌کند | در صورت نیاز واقعی به اشتراک کامپوننت بصری بین دو اپ در آینده، باید راه‌حل جداگانه (کپی آگاهانه یا بسته npm) اتخاذ شود |

## ADR-011: Soft Delete به‌جای حذف فیزیکی برای موجودیت‌های کسب‌وکاری حساس

**وضعیت:** Accepted

**زمینه:** حذف فیزیکی یک محصول یا کاربر که در سفارش‌های تاریخی ارجاع داده شده، باعث از‌دست‌رفتن یکپارچگی تاریخچه سفارش/گزارش می‌شود.

**تصمیم:** استفاده از ستون `deleted_at` (Soft Delete) در جداول `products`, `categories`, `users` به‌جای `DELETE` فیزیکی؛ اطلاعات سفارش نیز به‌صورت Snapshot در خود `order_items` نگه‌داری می‌شود (طبق سند شماره ۲) تا حتی با غیرفعال‌شدن محصول، سابقه سفارش دست‌نخورده بماند.

**جایگزین‌های بررسی‌شده:**
- **حذف فیزیکی مستقیم** — رد شد؛ ریسک از‌دست‌رفتن داده تاریخی و شکستن Foreign Key در جداول سفارش.

**پیامدها:**
- ✅ یکپارچگی تاریخی حفظ می‌شود؛ امکان Undo حذف در آینده.
- ⚠️ تمام Queryهای لیست باید صراحتاً `WHERE deleted_at IS NULL` را رعایت کنند (ریسک فراموشی) — پیشنهاد می‌شود در فاز پیاده‌سازی، این فیلتر در سطح Repository Layer به‌صورت پیش‌فرض اعمال شود تا فراموش نشود.
