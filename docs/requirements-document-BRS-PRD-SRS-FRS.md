# بخش A — سند نیازمندی‌های کسب‌وکار (BRS)

## A.1 چشم‌انداز و هدف کسب‌وکار

راه‌اندازی یک فروشگاه اینترنتی مستقل (Single-vendor B2C) که امکان فروش آنلاین محصولات را به مشتریان بدهد و تیم فروشنده بتواند از طریق پنل مدیریت، محصولات، سفارش‌ها و کاربران را به‌صورت متمرکز مدیریت کند. هدف اولیه، عرضه سریع یک نسخه قابل استفاده (MVP) و توسعه تدریجی قابلیت‌ها بر اساس بازخورد بازار است.

## A.2 ذی‌نفعان (Stakeholders)

| نقش | نوع ذی‌نفع | علاقه/مسئولیت اصلی |
|---|---|---|
| صاحب کسب‌وکار / مدیر محصول | Business Owner | تعریف اولویت، تأیید نیازمندی‌ها، تصمیمات کسب‌وکاری |
| Tech Lead / معمار نرم‌افزار | Internal | طراحی فنی، تضمین کیفیت معماری |
| توسعه‌دهندگان Backend/Frontend | Internal | پیاده‌سازی |
| تیم UI/UX | Internal | طراحی تجربه کاربری هر دو اپلیکیشن |
| تیم پشتیبانی/عملیات فروش | Internal (User of Admin Panel) | استفاده روزمره از پنل ادمین |
| مشتری نهایی | External | کاربر Storefront |
| درگاه پرداخت / سرویس پیامک-ایمیل | External Partner | ارائه‌دهنده سرویس ثالث |

**در محدوده (In-Scope) نسخه اول کسب‌وکار:**
- فروش آنلاین محصولات فیزیکی (کالای فیزیکی، نه دیجیتال/اشتراکی)
- یک فروشنده (Single-vendor)
- بازار هدف اولیه: [TBD - Business Decision] (فرض: بازار داخلی، زبان فارسی، واحد پول ریال/تومان)

- محصولات دیجیتال/اشتراکی/خدماتی

## A.6 مفروضات و وابستگی‌های کسب‌وکاری

- درگاه پرداخت مشخص و قرارداد آن از قبل در دسترس تیم فنی قرار می‌گیرد.
- سیاست ارسال (هزینه، زمان تحویل، مناطق تحت پوشش) توسط کسب‌وکار تعیین و قبل از Phase 1 نهایی می‌شود.
- سیاست مرجوعی/گارانتی به‌عنوان ورودی جداگانه از تیم کسب‌وکار دریافت می‌شود.

# بخش B — سند نیازمندی‌های محصول (PRD)

## B.1 بیانیه مسئله (Problem Statement)

کسب‌وکار نیاز به یک کانال فروش آنلاین دارد که هم تجربه خرید روان برای مشتری فراهم کند و هم امکان مدیریت متمرکز و کارآمد کاتالوگ، سفارش و کاربران را برای تیم داخلی بدهد؛ بدون وابستگی به پلتفرم‌های آماده که انعطاف‌پذیری محدودی دارند.

## B.2 چشم‌انداز محصول (Product Vision)

ساخت یک فروشگاه آنلاین قابل توسعه که در نسخه اول (MVP) چرخه کامل «مرور محصول → خرید → پرداخت → مدیریت سفارش» را پوشش دهد و در فازهای بعدی به یک پلتفرم فروش کامل با قابلیت‌های شخصی‌سازی، تخفیف، و تحلیل پیشرفته تبدیل شود.

## B.3 پرسونای کاربران (User Personas)

### پرسونا ۱ — مشتری (Customer)
- **هدف:** پیدا کردن سریع محصول موردنظر و خرید بدون دردسر.
- **نیاز کلیدی:** جستجو/فیلتر ساده، اطلاعات شفاف محصول، فرآیند پرداخت کوتاه و مطمئن، امکان پیگیری سفارش.
- **نقطه درد فعلی (فرض):** فرآیندهای خرید طولانی و عدم شفافیت وضعیت سفارش در جایگزین‌های موجود.

### پرسونا ۲ — مدیر محصول/کاتالوگ (Product/Catalog Admin)
- **هدف:** افزودن و به‌روزرسانی سریع محصولات و موجودی بدون نیاز به دانش فنی.
- **نیاز کلیدی:** فرم‌های ساده، آپلود تصویر آسان، مدیریت دسته‌بندی.

### پرسونا ۳ — مدیر سفارش/پشتیبانی (Order/Support Admin)
- **هدف:** رصد و پردازش سریع سفارش‌های جدید، تغییر وضعیت، پاسخ به درخواست مشتری.
- **نیاز کلیدی:** فیلتر و جستجوی سفارش، مشاهده جزئیات کامل سفارش و مشتری.

### پرسونا ۴ — مدیر ارشد (Super Admin)
- **هدف:** دید کلی از عملکرد فروشگاه و مدیریت دسترسی سایر کاربران ادمین.
- **نیاز کلیدی:** داشبورد آماری، مدیریت نقش و دسترسی.

## B.4 نقشه سفر کاربر (Key User Journeys)

**سفر ۱ — خرید موفق مشتری:**
ورود به سایت → مرور/جستجوی محصول → مشاهده جزئیات → افزودن به سبد → تکمیل اطلاعات ارسال → انتخاب/انجام پرداخت → دریافت تأییدیه سفارش → پیگیری وضعیت سفارش.

**سفر ۲ — پردازش سفارش توسط ادمین:**
ورود به پنل → مشاهده سفارش‌های جدید → بررسی جزئیات و موجودی → تغییر وضعیت سفارش (در حال پردازش → ارسال‌شده → تحویل‌شده) → اطلاع‌رسانی به مشتری (فاز بعد: خودکار).

## B.6 معیارهای موفقیت محصول (Product Success Metrics)

# بخش C — سند نیازمندی‌های نرم‌افزار (SRS)

                                              ├──> [Payment Gateway - External]
                                              └──> [Email/SMS Provider - External]

| NFR-002 | کارایی | زمان بارگذاری اولیه صفحه محصول Storefront (با SSR) | زیر ۲ ثانیه (شبکه متوسط) |
| NFR-003 | امنیت | تمام ارتباطات از طریق HTTPS | اجباری در تمام Environmentها |

| NFR-009 | قابلیت نگهداری | پوشش تست خودکار Backend | حداقل [TBD - هدف تیم، پیشنهاد ≥ 70%] روی منطق کسب‌وکار |

| NFR-011 | همزمانی | جلوگیری از Overselling موجودی هنگام ترافیک همزمان | تست بار مشخص روی سناریوی خرید همزمان یک کالای کم‌موجود |
| NFR-012 | بومی‌سازی | زبان پیش‌فرض فارسی + پشتیبانی راست‌به‌چپ (RTL) | تمام رابط کاربری RTL-safe |

## C.4 نیازمندی‌های واسط خارجی (External Interface Requirements)

| نوع واسط | جزئیات |
|---|---|
| رابط کاربری | Storefront (وب، ریسپانسیو، RTL) و Admin Panel (وب، دسکتاپ-محور) |
| واسط نرم‌افزاری - پرداخت | API درگاه پرداخت خارجی (REST/Redirect-based)؛ نوع دقیق درگاه: **[TBD - Business Decision]** |
| واسط نرم‌افزاری - اعلان | SMTP/Email Provider API و SMS Gateway API (Phase 2) |

## C.5 محدودیت‌های طراحی و پیاده‌سازی (Design Constraints)

طبق سند معماری اصلی: Backend با FastAPI (Python)، Frontend با Angular 22 به‌صورت دو پروژه مستقل در دو Repository جدا (Storefront و Admin Panel — طبق ADR-010 سند شماره ۴)، دیتابیس PostgreSQL، کش/صف Redis. هرگونه انحراف از این استک نیاز به تأیید Tech Lead و به‌روزرسانی سند معماری دارد.

## C.6 مفروضات و وابستگی‌های فنی

- درگاه پرداخت، SMS/Email Provider دارای مستندات API عمومی و پایدار هستند.
- زیرساخت میزبانی (Hosting) قبل از Production نهایی می‌شود.

| FR-AUTH-004 | Access Token باید کوتاه‌مدت و Refresh Token جهت تمدید نشست بدون ورود مجدد استفاده شود. | Must |
| FR-AUTH-005 | ادمین‌ها باید از طریق صفحه ورود مجزا و با اعمال RBAC وارد پنل شوند. | Must |

**Use Case کلیدی — UC-AUTH-01: ثبت‌نام مشتری**
- **پیش‌شرط:** کاربر ثبت‌نام نکرده.
- **جریان اصلی:** کاربر فرم ثبت‌نام را پر می‌کند → سیستم اعتبارسنجی می‌کند → حساب ایجاد و توکن صادر می‌شود → کاربر وارد سیستم می‌شود.
- **جریان جایگزین:** ایمیل/موبایل تکراری → نمایش خطای مشخص.
- **معیار پذیرش:** پس از ثبت‌نام موفق، کاربر بدون نیاز به ورود مجدد به حساب خود دسترسی دارد.

**Use Case کلیدی — UC-ORD-01: تکمیل خرید**
- **پیش‌شرط:** سبد خرید غیرخالی، موجودی کافی.
- **جریان اصلی:** کاربر آدرس را انتخاب/وارد می‌کند → سیستم مبلغ نهایی را محاسبه می‌کند → کاربر به درگاه هدایت می‌شود → پرداخت موفق → Webhook دریافت و تأیید می‌شود → سفارش ثبت قطعی می‌شود → تأییدیه به کاربر نمایش داده می‌شود.
- **جریان جایگزین ۱:** موجودی در لحظه پرداخت کافی نیست → کاربر مطلع و مبلغ بازگردانده می‌شود (Refund).
- **جریان جایگزین ۲:** پرداخت ناموفق/لغو توسط کاربر → سفارش در وضعیت «پرداخت‌نشده» باقی می‌ماند تا مهلت انقضا.
- **معیار پذیرش:** موجودی هرگز منفی نمی‌شود؛ وضعیت سفارش همیشه با نتیجه واقعی Webhook همخوانی دارد نه صرفاً ریدایرکت مرورگر.

# بخش F — واژه‌نامه (Glossary)

| اصطلاح | تعریف |
|---|---|
| Variant | نسخه مشخص یک محصول (مثلاً رنگ/سایز) با قیمت و موجودی مستقل |

# بخش G — معیار پذیرش کلی و Definition of Done

یک نیازمندی/ویژگی زمانی «تکمیل‌شده» تلقی می‌شود که:
1. پیاده‌سازی مطابق شرح FR/Use Case مربوطه باشد.
2. تست خودکار (Unit/Integration) مرتبط نوشته و سبز شده باشد.
3. مطابق NFRهای مرتبط (امنیت، کارایی) بررسی شده باشد.
4. در محیط Staging توسط QA/صاحب کسب‌وکار تأیید (UAT) شده باشد.
5. مستندات API (در صورت افزودن endpoint جدید) به‌روزرسانی شده باشد.
